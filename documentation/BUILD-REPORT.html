Phase 2 — authentication and access control

Three portals share one API, so the central question is who may do what. Phase 2 answers it in four layers, all enforced on the server. Hiding a button in React is a courtesy, never a control — every one of these rules is re-checked by the API on every request.

LayerHow it works
PasswordsArgon2id (memory-hard, winner of the Password Hashing Competition). Stored hashes begin $argon2id$. A leaked database does not hand out passwords.
Sessions15-minute access JWT kept in memory; long-lived refresh token in an HttpOnly cookie that JavaScript cannot read. Every refresh rotates the token and revokes the previous one.
Reuse detectionIf an already-rotated refresh token is presented again, a copy has leaked: the entire session family is revoked and the event is logged.
AuthorisationA global guard denies everything by default; routes must opt in with @Public(). Staff routes then need an explicit permission such as withdrawal:approve. Portal type is checked separately, so a customer token can never act as staff.
Account protection5 failed logins lock the account for 15 minutes; Redis-backed rate limits on every sensitive route return 429 with a "wait N seconds" message.
EvidenceAn append-only audit table records every registration, login, failure, lockout, password change and permission change — with IP, user agent and before/after values, and never a password or token.

How to view the live app yourself

A localhost link cannot work from your computer — that address only exists inside the sandbox machine where the code runs. Use the preview panel in this conversation instead: any server I start (the web app on port 5173, the API on port 4000) appears there as a live, clickable preview.

If the preview is not visible, ask me to restart the servers — the sandbox resets between sessions, which stops the processes and wipes the installed packages, but never touches your code.

Rebuilding from a cold sandbox

# one command: services + install + migrate + seed
npm run setup

# then start both servers (preview appears automatically)
npm run dev

# verify
npm test            # 61 tests against a real, isolated Postgres + Redis
bash scripts/smoke.sh
node scripts/capture-phase2.mjs       # browser journey + refresh these screenshots
python3 scripts/build-report.py       # regenerate this page

Known limitations after Phase 2

  • Email and SMS are console drivers. Codes print to the API log, and in development are also returned to the browser so the flow can be tested without spend. A real provider plugs into MessagingService in Phase 7 without touching the auth code.
  • No staff 2FA yet. Recommended before real money moves; the TOTP storage and verification plumbing already exist.
  • No CAPTCHA. Lockout and rate limiting cover the basics; add Turnstile if abuse appears.
  • Not yet built: rider document upload, staff/role management screens, audit-log viewer, session list. The APIs exist; the screens arrive with Phases 4–5.
  • Payments remain simulated (PAYMENTS_MODE=DEVELOPMENT) until the live keys are placed in the server's .env — never in this workspace.
