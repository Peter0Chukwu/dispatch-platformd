WHAT YOUR TWO SCREENSHOTS SHOW
------------------------------
Image 1 (Networking): traderswelfarelogistics.online is linked to port 80 of the
WEB service. That is correct, and it is why the site loads.

Image 2 (Environment variables): this is the WEB service's environment, and it
contains FRONTEND_URL. That variable does nothing here. The web container only
reads API_UPSTREAM (and the VITE_* values, which are baked in at build time).

FRONTEND_URL is read by the API service — it is what the API puts inside
verification and reset emails. If it is set on the web service and not on the API
service, the API falls back to the first entry of CORS_ORIGINS, which is how you
ended up with www links and then a bare-domain link from different builds.

WHERE EACH VARIABLE BELONGS
---------------------------
WEB service (what you screenshotted):
  API_UPSTREAM            internal address of the API, e.g. api:4000
  VITE_GEOAPIFY_API_KEY   build-time only: rebuilding is required after changing it
  FRONTEND_URL            <- delete it here, it is doing nothing

API service:
  FRONTEND_URL=https://traderswelfarelogistics.online
  CORS_ORIGINS=https://traderswelfarelogistics.online,https://www.traderswelfarelogistics.online
  EMAIL_MODE=RESEND
  RESEND_API_KEY=re_...
  EMAIL_FROM="Traders Welfare Logistics <no-reply@traderswelfarelogistics.online>"
  (plus DATABASE_URL, REDIS_URL, JWT secrets, PAYSTACK_*, TERMII_*, GEOAPIFY_API_KEY)

WHY BOTH ORIGINS IN CORS_ORIGINS
--------------------------------
www now resolves and serves the site, so somebody can land on www and sign in
there. If www is not in CORS_ORIGINS, the page loads and sign-in fails. Listing
both costs nothing.

WHAT THIS COMMIT ADDS
---------------------
The API now says the answer at boot, in the deploy log:

  Email links will point at: https://traderswelfarelogistics.online

and warns if that address is not in CORS_ORIGINS — the silent case where the link
opens but the page cannot sign anyone in. GET /api/v1/health also reports it:

  "integrations": { "site": "https://traderswelfarelogistics.online", ... }

So the next time a link looks wrong, one request tells you which address the API
actually believes it is.

Underneath, FRONTEND_URL may hold a list by mistake and only the first filled-in
entry is used — for email links and for the payment return URL alike.

TO APPLY
--------
1. Add FRONTEND_URL and CORS_ORIGINS to the API service (not the web service).
2. Delete FRONTEND_URL from the web service.
3. Deploy this commit and restart the API.
4. Check /api/v1/health: integrations.site should read the bare domain, and
   email should read RESEND.
5. Request a fresh password reset and confirm the link opens the reset page.
